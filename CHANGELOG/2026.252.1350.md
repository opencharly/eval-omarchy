# 2026.252.1350 — fix(lane): placeholder substitution control at bed-render + local-ollama default

## Summary

The full lane R10 (eval-lane-plan, 14 previous-config PRs through the implemented lane management) exposed a missed control: the triage agent's plan JSON returned PLACEHOLDER values ("drive": "$drive" - the model echoed the prompt's placeholder) and the bed-render shipped a bed with an EMPTY sha (pr-apply 10144&nbsp;&nbsp; - unbound variable at run). The bed-render's validate only ran charly-box-validate (syntax), never the substantive check.

Fixes:

1. **The placeholder control (the missed control, RCA 2026.252.1206)**: the bed-render's validate now REJECTS a rendered bed carrying placeholder strings or an empty sha - at render time, never shipping to a real bed.
2. **The oracle prompt**: NEVER emit placeholders - every field must be a real resolved value from the tools; a placeholder fails the lane at render.
3. **Local-ollama default** (RCA 2026.252, the lane 401): the lane's LLM endpoint defaults to the LOCAL ollama server - implemented in opencharly/plugin-pipeline#9 (the authored entity llm block + the env-override layer + the built-in default, uniform precedence, the header only when the key is non-empty). The candy's dead var entries (which never reached the plugin process) are removed; the env_accept contract (the operator override layer) stays - all three option layers work.
