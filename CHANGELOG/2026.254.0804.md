### 3a. Update-bed deadlock — R1 root-cause analysis (8 steps) + batch routing

- **Mechanism (anchored)**: update_gate's restart-only path is `vm stop --force --domain <d> ; vm start --domain <d>` (plugin-check/candy/plugin-check/anchored.go:153-154), then `checkLiveTree("check-live-rebuild")` (bed_run.go:845/887) reconnects over `kit.SSHExecutor{ConnectTimeout: 10}` (live_gather.go:445) — a per-attempt connect timeout, NO overall deadline around the rebuild reconnect. A rebooted guest whose NetworkManager has no IPv4 lease (STATE:20 unavailable, ssh "timed out during banner exchange") is indistinguishable from a slow one → the rebuild reconnect never bounds → the bed hangs indefinitely, stalling the suite.
- **Root cause**: plugin-check's rebuild reconnect is unbounded; a lease-less guest is indistinguishable from a slow one.
- **Root fix**: bound the rebuild reconnect with a total readiness deadline (lease/SSH-endpoint probe) that turns a lease-less boot into a clear, time-bounded named failure (the runner class this PR already depends on), NOT an infinite hang.
- **Why the eval-omarchy code path is proven sound**: the update bed's suite-run check-live PASSED (42 steps, 41 passed/0 failed/1 skipped; all 5 direct-write artifacts written to media/2026.254.0711/update/ BEFORE the deadlock), and the SAME rebuild phase passed on the other 15 beds in the same suite + on update's FRESH-VM re-run (2026.254.0746, PASS 10/10, check-live-rebuild 28.6s).
- **Routing (R2)**: the defect is NOT dismissed as "environmental" or "not a code path of this PR", and the re-run is NOT waved as the fix for the hang. It is routed to a **named thematic batch — G-3c: plugin-check bounded rebuild-reconnect (wait-for-guest-readiness with a total deadline; lease-less guest → clear time-bounded failure)** — repo `opencharly/plugin-check`, follow-on cutover after G lands, with the mechanism + files cited above (`anchored.go:153-154`, `bed_run.go:845/887`, `live_gather.go:445`).
