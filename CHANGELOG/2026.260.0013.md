# 2026.260.0013 — feat(eval): wire the `vision:` verb into the PR-eval bed — assert the captured screenshot

## Summary

The eval bed already captures the live VM's display (`spice: screenshot` →
`/tmp/pr-<N>.png`). This adds a `vision:` step that ASKS A MODEL ABOUT THAT IMAGE
— the use case the verb exists for: "does the applied PR actually render a working
desktop", judged from the pixels, not from a grep of the source.

**What changed (4 files: lane config + the entry skill's applicability map + the README overview + the media-contract doc):**

`candy/eval-pr/charly.yml` (the entry skill the grading stage reads):
- the applicability map gains a row for the new judgement — a visual PR is graded
  on whether the captured screenshot shows a rendered desktop, with the evidence
  locus `@gate.eval_steps` entry `screen-vision-judged`.


`charly.yml`:
- the eval-pr bed's `add_candy` gains
  `@github.com/opencharly/plugin-vision/candy/plugin-vision:v2026.259.2147`;
- a new `screen-vision-judged` step after `rec-screen-spice`: it reads the SAME
  `/tmp/pr-<N>.png`, asks the model for a single YES/NO judgement (is this a
  rendered desktop with a panel, not a blank/error screen), and asserts
  `expect: {contains: "yes"}`. The step is in the treatment bed only (the control
  bed renders `${checks:negate}` with no apply), so it is the PR's applied UI being
  judged.

`docs/evidence-and-media.md`:
- a new "The screenshot is JUDGED, not just captured" section documenting the step
  (the media contract previously described only CAPTURE).

`README.md`:
- the EVAL step now states the captured screenshot is judged, so the lane's overview
  matches what the bed does.

**Why the id is `screen-vision-judged` and NOT `rec-screen-vision`.** The
pipeline's bed-outcome reader excludes every `rec-`-prefixed id (source, below),
because media presence is not verification. An earlier revision of this PR named
the step `rec-screen-vision`, which meant its verdict was DROPPED from the gate's
`eval_steps` — the check ran but did not COUNT. The rename makes it a counted
verification step alongside `pr-apply`. (This was caught by fact-checking the
docs against the harness source — R1.)

**Why the assertion is value-gated.** An earlier draft asked for a JSON judgement
and matched the key `"desktop"` — a token present in every reply, so
`{"desktop": false}` would have passed. A single-word YES/NO cannot be satisfied by
a false verdict, so the check genuinely fails on the condition it claims to detect.
