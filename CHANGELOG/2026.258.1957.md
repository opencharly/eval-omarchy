# 2026.258.1957 — feat(eval): the minimal omarchy PR-eval lane (eval-pr-plan) — one self-contained eval/pr-<N>/ per PR

## Summary

**R5 cutover** of the omarchy PR-eval lane: replaces the 18-stage v1 lane (`eval-lane` candy +
`eval-lane-plan`) with one 11-stage lane, `eval-pr-plan`, whose every evaluation is ONE
self-contained `eval/pr-<N>/` directory.

### What v2 is

```
eval/pr-<N>/
├── charly.yml   # both beds: check-omarchy-pr-<N>-vm (treatment) + -control, COMMITTED
├── eval.yml     # the single record: oracle + eval + control + gates + cold-read
│                #   + the user-voice report + media links, COMMITTED
└── media/       # the recordings (.cast/.gif/.mjpeg/.mp4/.png), GITIGNORED
```

- **The config oracle PICKS the golden** (`check-omarchy-eval-<channel>-inst:golden`), a
  render-time enum validated against the four-golden registry.
- **Render-once-per-`pr@sha`**: the engine `cache:` block reads the committed `eval.yml` and the
  oracle NEVER re-runs on an unchanged head.
- **One template renders both beds** via per-marker transforms (`${checks}` / `${checks:negate}`),
  so treatment and negative control share ONE discoverable file.
- The deterministic gates (`executed_checks>=1`, `control_ok`, `media_ok`) and the structured
  step rows come from `ledger_gate` (the pipeline `media.min` is the single source).
- Stage list: `oracle → render → control → eval → media → gate → report → cold-read → record →
  not-testable → publish`.

### Deleted (v1, R5)

`candy/eval-lane/`, `eval-lane-plan`, the `pr-beds/` layout + its `discover:` path, the
`metrics/` + `setup-defects/` artifacts, and the stale `eval/pr-*.md` reports. The acceptance
corpus (`check-omarchy-accept-*`, the `omarchy-corpus` candy) is untouched.

### Engine dependency (merged)

This lane consumes four engine primitives merged in `plugin-pipeline` **v2026.257.1506**
(PR #23): the agent `cache:` block, per-marker generate transforms (`:negate`/`:json`/`:yaml`/
`:indent`/`:bullets`), the ADE bed resolved by ENTITY NAME (a prior flat-`plan`/`pr-beds`
hardcode returned a vacuous `PASS code=0`), and `ledger_gate` honoring the pipeline `media.min`
+ surfacing step rows. Pinned as `plugin-pipeline/candy/plugin-pipeline:v2026.257.1506`.

### The redo-trigger wiring — a THIRD real defect, fixed in this tree (R1)

Reaching the above PASS surfaced a third defect, at the reviewed head
`fix(eval): key the ade stages' redo trigger as setup-defect`: the `ade` stage signals a
`fail_on` verdict with the trigger **`setup-defect`** (plugin-pipeline `executor.go`), but the
`control`/`eval` stages' `redo.triggers` mapped **`redo-plan`/`redo-run`** — keys the `ade`
stage never emits. With the trigger unmapped, the executor's redo target stayed the trigger
name, no stage matched it, and the chain flowed ON: a control failure (a caught FAKE
known-red assertion) was NEVER re-authored, contradicting the oracle skill's own control
contract ("read the failing step, RE-AUTHOR that check"). `stage-findings.yml` recorded
`trigger: setup-defect` unfired. The fix keys `setup-defect -> oracle`, so the contract's
informed redo actually runs.

### The record `validate` script — TWO real defects fixed, then proven by the lane

The record stage's `validate:` script is part of this diff and had two real defects the live
run surfaced (R1), both the SAME root cause: the record's report prose is a YAML **block
scalar** (`report: |-`), so its lines are INDENTED, while the checks anchored at column 0.

1. The `^\*Assisted-by:` / `^\*Tested-by:` checks rejected the indented footers.
2. The `^## Tests` .. `^## Suggestions` range for the outcomes check matched nothing, so it
   reported `record: Tests lacks observed outcomes` on a valid record.

Both are fixed in this PR (accept optional leading whitespace; the banned verdict-language is
anchored to a comment/heading so the record's own `verdict:` field is not caught), and the
fix is PROVEN by the completed lane above: `[stage record] ok` with
`eval/pr-11803/eval.yml` rendered and all five media artifacts asserted.

### The `update_gate` disclosure (T3)

The bed template changes `update_gate: restart-only` → `update_gate: skip` on BOTH the
treatment and the control bed. Disclosed and justified: the per-PR beds are `from:
<golden>` CLONES whose whole point is to apply the PR at RUNTIME via `pr-apply`, then observe.
There is no "fresh update/rebuild" of a clone to gate — a `charly update` would re-clone and
DISCARD the applied PR, destroying the surface under test. `update_gate: skip` is therefore
correct for these beds (the golden's own provisioning is gated separately by
`check-omarchy-eval-base-inst`, which is NOT skipped). The engine's own R10 sequence for the
clone (build → create → deploy-add → check-live) still runs in full; only the meaningless
"rebuild a clone" leg is skipped.
